Lojipsa

재료 시세 API 캐시 적용으로 공식 API 호출을 없애 응답속도 91% 개선

avg 207ms → 18ms · p95 529ms → 26ms · 운영 서버 JMeter 실측

운영 배포 · 실측 expand_more

원인

기능은 정상이었지만 요청마다 로스트아크 공식 API를 순차로 3회(아이콘 1 + 재료 2) 호출했습니다. 응답시간이 재료 수에 비례해 늘고, 방문자가 늘면 스케줄러와 공유하는 API 키 호출도 그대로 늘어나는 구조였습니다.

해결

시세가 일별 통계라는 점에 맞춰 5분 TTL 캐시를 적용했습니다. 만료 순간 갱신을 직렬화해 외부 호출을 1회로 묶고, 일부 실패한 결과는 캐시하지 않으며, 관리자 변경 시 즉시 무효화합니다.

추가 판단

로컬 curl은 네트워크에 따라 흔들려서 근거로 쓰지 않았습니다. 운영 서버에 같은 조건으로 배포 전후를 각 3회 측정했고, 공식 API 호출 횟수는 Mockito 단위 테스트로 검증했습니다.

항목 개선 전 개선 후 변화
평균 응답속도 207ms 18ms -91%
p95 응답속도 529ms 26ms -95%
p99 응답속도 819ms 176ms -79%
요청당 공식 API 호출 3회 0회 (캐시 적중) -100%

측정 조건: 운영 서버(EC2 t3.micro) 대상, JMeter 1 스레드·3초 간격·120초·3회 평균(개선 전 110건, 개선 후 117건, 에러 0). 공식 API 한도와 알림 스케줄러 영향을 피하려고 저부하로 측정했습니다. 네트워크 기준선(외부 호출 없는 엔드포인트)은 평균 18ms로, 개선 후 응답이 사실상 이 기준선에 닿았습니다. 개선 후에는 20 스레드로 60초(5,446건) 부하도 에러 없이 평균 11ms·p95 17ms로 처리했습니다(개선 전은 같은 부하를 걸면 공식 API 한도에 걸릴 수 있어 측정하지 않았습니다).

Lojipsa

보석 시세 API는 데이터 성격에 맞춰 TTL을 1분으로 잡아 응답속도 92% 개선

avg 436ms → 37ms · p50 369ms → 10ms · 운영 서버 JMeter 실측

운영 배포 · 실측 expand_more

원인

재료 시세와 같은 구조로, 요청마다 공식 경매장 API를 보석 수만큼 순차 호출했습니다. 실측 평균이 436ms로 재료 시세(207ms)보다 더 무거웠습니다.

해결

같은 캐시 구조(갱신 직렬화, 일부 실패 시 미캐시, 관리자 변경 시 무효화)를 적용하되 TTL은 1분으로 따로 잡았습니다. 재료 시세는 일별 통계라 5분이 안전하지만, 보석은 경매장 최저가라 실시간에 가깝기 때문입니다.

추가 판단

p95/p99가 재료만큼 내려가지 않은 건 의도된 비용입니다. 1분마다 한 요청은 캐시를 갱신해 느려지는데(39건 중 3건이 258~629ms), 신선도를 위해 이 꼬리를 감수했습니다.

항목 개선 전 개선 후 변화
평균 응답속도 436ms 37ms -92%
p50 응답속도 369ms 10ms -97%
p95 응답속도 914ms 218ms -76%
p99 응답속도 1,306ms 445ms -66%

측정 조건: 운영 서버(EC2 t3.micro) 대상, JMeter 1 스레드·3초 간격·120초·3회 평균(개선 전 103건, 개선 후 117건, 에러 0). 공식 API 한도와 알림 스케줄러 영향을 피하려고 저부하로 측정했습니다. 개선 후 20 스레드로 60초(5,478건) 부하는 에러 없이 평균 10ms·p95 13ms·p99 25ms로 처리했습니다. 캐시 적중 시 공식 API 호출이 없다는 점은 Mockito 단위 테스트로 검증했습니다.
